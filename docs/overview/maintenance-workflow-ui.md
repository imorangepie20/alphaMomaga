# 유지보수 작업 처리 화면

## 원인과 업무 연결

2026-09-05 확인 결과 `/maintenance`는 작업 목록만 표시했다. API에는 자산을 참조하는 작업 등록과
예정일·상태 수정, 권한 검사 및 DB 감사 기록이 있었지만 화면에 변경 경로가 없었다.

유지보수는 자산에 연결되며 계약·청구·수납 레코드를 변경하지 않는다. 완료 상태는 자산 운영 화면의
미완료 업무 집계에서 제외된다.

## 구현

### 2026-09-05 완료 기록 확장

- 원인: 기존 완료 처리는 상태만 저장해 실제 작업일과 수리 결과를 확인할 수 없었다.
- `completedAt`(서울 기준 날짜)와 `resolution`(최대 4,000자)을 API·DB·폼에 추가했다.
  새 완료 등록 및 수정은 두 값이 필수다. 존재하지 않는 날짜와 미래 날짜,
  빈 결과는 거부하며 예정일보다 빠른 실제 완료는 허용한다.
- 기존 완료 레코드는 날짜를 추정해 채우지 않고 `완료일 기록 없음`으로 조회한다.
  이러한 레코드를 완료 상태로 수정하려면 누락된 증빙도 함께 입력해야 한다.
- 완료 상태를 다른 상태로 바꾸면 현재 완료 증빙을 비운다. DB 트랜잭션의 감사 기록에
  변경 전 완료일·처리 결과를 남긴다. 행 잠금 후 병합·검증하며 실패 시 저장하지 않는다.
- 폼은 완료일을 자동으로 오늘로 채우지 않고 실제 날짜를 입력받는다.
  실패해도 입력을 유지하며 완료 기록을 목록에서 확인할 수 있다.
- 별도 리뷰에서 장시간 열린 페이지의 이전 날짜 제한을 발견했다.
  서울 자정을 넘긴 회귀 테스트를 추가하고 모달 열기·완료일 포커스·날짜 입력 시
  제한 날짜를 갱신하며 제출 검증은 현재 서울 날짜를 사용하도록 수정했다.
- 마이그레이션 `0003_cuddly_professor_monster.sql`은 nullable 컬럼 두 개만 추가한다.
  격리 DB에서 검증 후 개발 DB에 사전 custom-format 백업을 확보하고 적용했다.
  백업은 `property-manager-postgres:/tmp/pre-maintenance-completion-20260905.dump`에 있다.
  이는 같은 컨테이너 안의 임시 안전 사본이며 외부 운영 백업을 대신하지 않는다.
- 검증: API 단위 219개, 인메모리 통합 27개, 격리 PostgreSQL 완료 기록 테스트 1개,
  웹 173개, API 빌드·Oxlint 및 웹 변경 파일 ESLint·TypeScript 통과.
  PostgreSQL 검사는 재연결 후 증빙 유지, 실패한 정정의 롤백, 재작업 감사 기록을 확인한다.
  실제 로그인 Chromium의 1280px·390px 완료 폼 배치·취소 2개 검사도 통과했다.
  브라우저에서 실제 운영 작업을 완료하거나 테스트 레코드를 생성하지 않았다.

아래는 최초 등록·수정 UI 구현 이력이다. 완료 증빙은 위 확장이 현재 동작이다.

- 작업 등록: 자산, 작업 내용, 예정일, 상태를 입력한다. 공백 작업 내용을 거부하고 저장 중 재요청을 차단한다.
- 일정·상태 수정: 기존 `PUT /maintenance/:id` 계약에 맞게 예정일과 상태만 전송한다.
  기존 자산과 작업 내용은 읽기 전용이다. 작업 내용 정정 기능은 API 확장 후 제공해야 한다.
- 작업 시작: 대기·예정 작업을 `InProgress`로 변경한다.
- 완료 처리: 진행 중 작업에서 완료 확인 창을 열고 저장하면 `Completed`로 변경한다.
- 모든 변경은 `/api/proxy/maintenance`를 통해 서버 세션 인증과 API의 `maintenance:manage` 검사를 거친다.
  인증 만료·권한 부족·입력 오류는 화면에 표시하며 실패 시 폼을 유지한다.
- 전체 작업 기준 지표, 검색, 자산·상태 필터, 기한 초과 전용 필터와 빈 결과 안내를 제공한다.
- 서울 기준일보다 예정일이 이전인 미완료 작업만 기한 초과이다. 오늘 예정 작업과 완료 작업은 제외한다.
  정렬은 기한 초과, 미완료, 예정일, ID 순이다.
- 모달은 화면 높이를 제한하고 내부 스크롤을 사용한다. 기존 공통 폼 간격과 테마 컴포넌트를 사용한다.
- `getMaintenanceWorkspace`는 자산과 유지보수 API만 조회하며 실패 시 예시 데이터를 표시하지 않는다.

## 반복 작업 조사

화면의 `보일러 점검`, `2026-12-01`은 `api/test/operations.e2e-spec.ts`의 생성 데이터와 일치한다.
해당 테스트는 생성 후 상태를 `Scheduled`로 바꾸고 앱을 종료하지만 생성 레코드를 삭제하지 않는다.
DB를 연결한 상태에서 반복 실행했다면 잔여 레코드가 생길 수 있다. 이는 코드에 근거한 가능성이며,
실제 레코드의 생성 주체는 확인하지 않았다. 기존 데이터를 삭제하거나 자동 병합하지 않았다.
이번 작업에서는 해당 테스트를 운영 DB에 실행하지 않았다.

## 후속 확장

담당자 배정, 작업 내용 정정, 비용·첨부파일과 작업 이력 상세는 현재 모델에 없는
후속 기능이다. 이번 변경은 기존 API의 등록·일정·상태 처리 흐름을 완성한다.
