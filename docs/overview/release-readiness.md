# 운영 준비 검수

## 판단 기준

화면이 존재하거나 테스트가 통과했다는 이유만으로 프로젝트 전체 완료를 선언하지 않는다.
자산 → 임차인 → 계약 → 월별 청구 → 실제 수납 → 정정 및 미수 복구와
유지보수·점검·관리자 권한 흐름을 실제 데이터 저장 및 인증 경계까지 확인한다.

## 최신 판정 요약

- 자산·임차인·계약·유지보수·점검 등록창은 로그인 Chromium의
  1280x900 및 390x844 화면에서 열기·취소, 화면 내 배치와 가로 넘침 검사
  총 10개를 통과했다. 변경 API 요청은 차단했고 발생 수 0건을 확인했다.
  이 증거는 폼 접근과 반응형 배치에 한정된다. 실제 저장·오류 복구,
  키보드 전용 조작과 다른 기기·브라우저 검수를 대신하지 않는다.

- 실제 로그인 세션의 자산 화면·수납 원장 조회와 취소 확인창 미리보기 검수를 추가했다.
  조회 성공은 확인했지만 수납 생성·실제 void의 인증된 브라우저 성공은 아직 미검증이다.
  후자의 테스트는 전용 테스트 데이터로만 실행한다.

- 검증 대상 커밋: `576a1e8`.
- API 원격 CI `33938701720` 성공: 품질 검사와 전용 PostgreSQL 작업 모두 통과.
- 웹 원격 CI `33939051293`(`2dd34fc`) 성공. Auth0 검사용 구성 추가 후
  비로그인 브라우저 단계를 포함한 전체 workflow 통과를 확인했다.
- 아래 날짜별 기록은 당시 결과다. 이전 실패나 테스트 수를 최신 상태로 해석하지 않는다.
- 실제 로그인 후 등록·수정·수납·취소, 역할별 접근 및 모바일 검수는 미완료다.
- Auth0 초대·권한 변경·차단의 실계정 검수, 운영 백업 자동화 및 장애 대응 검수도 남아 있다.
- 호실 원장 기반 점유율, 비용 원장, 유지보수 담당자·비용·증빙,
  점검 체크리스트·증빙 및 설정 영속 수정은 별도 개발 대상으로 유지한다.
  CI 성공은 이러한 업무 기능의 구현 완료를 뜻하지 않는다.

## 남은 검수와 개발

후속 검증으로 격리 PostgreSQL 및 소규모 백업·복원 리허설은 통과했다.
각 항목의 전체 운영 요건이 모두 완료된 것은 아니며 아래 추가 결과와
`docs/overview/database-recovery.md`에서 검증 범위를 구분한다.

1. 운영 DB와 분리된 PostgreSQL 환경에서 migration, 수납 저장·중복·void·동시성 검증.
2. 실제 로그인 세션에서 역할별 접근과 등록·수정·실패 복구 및 모바일 폼 검수.
3. 테스트 전용 Auth0 계정으로 초대 링크 사용·역할 변경·차단을 검증하고
   기존 토큰의 권한 유효기간과 관리자 감사 기록 정책을 확정.
4. 백업 및 복원 리허설, 운영 배포·재시작·장애 관찰 절차 검증.
5. 기존 문서에 남긴 고급 기능을 구현 또는 명시적인 범위 결정으로 정리.
   호실 원장 기반 점유율, 비용 원장, 시스템 설정 영속 수정 등의 미구현 사항을
   화면에서 제공되는 것으로 오인하게 만들지 않는다.

위 항목은 이번 테스트만으로 완료되지 않았다. 후속 작업자는 검증 근거를 추가하며 진행한다.

## 격리 PostgreSQL 검증 추가

- 운영 DB와 다른 임시 `postgres:16-alpine` 컨테이너의 빈 DB에 migration 3개를 적용했다.
- PostgreSQL 통합 테스트를 보강하고 통과했다. 동시 청구 생성의 유일성,
  부분 수납·void 복구, 잔액을 초과하는 두 동시 수납 중 한 요청만 성공,
  API 인스턴스 재생성 후 잔액·취소 영수증 보존, 동시 void의 단일 잔액 복구를 검증했다.
- 테스트는 이제 `DATABASE_URL`만 설정해서 실행되지 않는다.
  별도 폐기 가능한 DB의 `TEST_DATABASE_URL`을 명시해야 한다.
  테스트 중에만 해당 값을 애플리케이션 DB 설정으로 적용하고 원래 환경을 복구한다.
  월별 생성 API는 DB 전체 활성 계약을 대상으로 하므로 운영 DB를 지정하면 안 된다.
- 재현: 임시 DB에 `DATABASE_URL`로 `npm.cmd run db:migrate`를 실행한 뒤,
  동일 DB를 `TEST_DATABASE_URL`로 지정하고
  `npm.cmd run test:e2e -- billing-postgres.e2e-spec.ts --no-file-parallelism` 실행.
- 이 결과는 단일 청구의 경쟁 조건과 API 인스턴스 재생성 검증이다.
  대규모 부하, DB 장애 복구, 실제 백업 복원 검증을 대신하지 않는다.

## 백업·복원 검증 추가

- 임시 원본 DB를 custom-format으로 백업하고 별도 빈 DB로 복원했다.
- 10개 업무 테이블의 행 수·내용 지문 및 migration 이력 3개를 확인했다.
- 복원 DB에서 PostgreSQL 수납 통합 테스트를 다시 통과했다.
- 절차와 수량은 `docs/overview/database-recovery.md` 참고.
  예약 백업·외부 보관·운영 규모 복구 시간·Auth0 복구는 별도 후속 요건이다.

## 청구 합계 기준 정정

- 발견: API 월별 요약과 임차인 원장 합계는 초안·취소 금액까지 더했으나,
  자산·수익 화면은 확정 청구만 합산해 동일 월에도 금액이 달라질 수 있었다.
- 변경: `billing-summary`와 임차인 원장 금액은 `Draft`, `Cancelled`를 제외한다.
  승인 대기·취소 건수 및 원장 개별 청구 기록은 보존한다. DB 원본 금액은 수정하지 않는다.
- 기본 대시보드와 수납 화면에 확정 청구 합계 기준을 명시했다.
  두 화면의 조회 오류 처리도 JSX 렌더링과 분리해 React 린트 오류를 해결했다.
- 기존 테스트가 초안 포함 금액을 기대해 오류를 놓쳤다. 확정 금액 기대값으로 바로잡고,
  취소·초안만 있을 때 금액 0 및 취소 기록 보존 테스트를 추가했다.
  수정 전 실패를 확인한 뒤 API 단위 테스트 208개와 인메모리 통합 21개를 통과했다.
- 웹 144개 테스트, 변경한 두 화면 ESLint 및 API·웹 빌드 통과.

## 수납 임차인 조회 장애 처리

- 발견: 수납 화면의 `getTenants()`가 설정 누락·HTTP 오류·네트워크 장애에
  고정 예시 임차인 4명을 반환해 실제 원장과 다른 이름을 연결할 위험이 있었다.
- 변경: 예시 대체를 제거하고 조회 실패를 호출자에게 전달한다.
  정상 빈 목록은 그대로 유지하며 배열이 아닌 응답은 거부한다.
  수납 페이지는 기존 오류 안내를 표시하고 등록 UI를 렌더링하지 않는다.
- 검증: 설정 누락, 401·403·500·503, 네트워크 오류, 잘못된 응답,
  정상 빈 목록 및 실제 목록에 대한 테스트와 페이지 오류 렌더링 테스트 추가.
  웹 전체 154개 테스트 및 변경 파일 ESLint 통과.

## 공개 조회 API 차단

- 자산·임차인·계약·기존 결제·정비·점검 목록 API의 비로그인 접근 누락을 발견하고 수정했다.
  외부 Cloudflare 경로의 HEAD 상태가 6개 모두 200에서 401로 바뀐 것을 확인했다.
- 웹 업무 조회도 서버 세션 토큰을 전달하도록 함께 변경했다.
  허용 API origin 검사, 리디렉션 거부, 캐시 비활성화를 적용했다.
- API 단위 208개·인메모리 통합 27개·웹 157개 테스트 통과.
  자세한 경계는 `docs/architecture/web-auth-boundary.md` 참고.

## 청구월 입력 검증

- 발견: 청구·영수증 조회 및 요약 API가 잘못된 월을 검증하지 않아 빈 결과나 0원처럼
  해석될 수 있었다. 수납 화면도 해당 값을 그대로 요청했다.
- 변경: 조회·요약·임차인 원장·청구 생성 API의 청구월을 유효한 4자리 연도와
  01~12월의 `YYYY-MM`으로 검증한다. 잘못된 값은 조회 전에 400으로 거부한다.
  전체 청구·영수증 조회의 월 생략은 계속 허용한다.
- 수납 화면은 잘못된 월이나 반복 query parameter를 감지하면 API를 호출하지 않고
  월 선택 안내를 표시한다. 임의로 다른 월의 금액을 보여주지 않는다.
- API 회귀 테스트에서 6개 잘못된 값의 거부를 확인했다. API 전체 214개 및
  인메모리 통합 27개 테스트 통과. 웹 화면 검증도 5개 오류 입력을 추가했다.
- 웹 전체 162개 테스트, 변경 화면 ESLint·타입 검사 및 API 빌드 통과.
- 브라우저 도구에 연결된 세션이 없어 실제 로그인 후 검수는 사용자에게 연결을 요청한 상태다.

## CI 검증 단계 보강

- API CI가 `TEST_DATABASE_URL`을 전달하지 않아 PostgreSQL 테스트를 건너뛸 수 있었다.
  전용 서비스 DB의 값을 명시하고 PostgreSQL 테스트를 독립 실행한다.
- 인메모리 통합 테스트는 API 품질 작업에서 별도로 실행하며 Oxlint 단계도 추가했다.
- 웹 CI에 누락된 `npm test`를 추가했다. API 준비 확인은 공개 상태 확인 경로인
  `/health/database`를 사용한다. 자산 목록의 인증을 완화하지 않는다.
- 로컬 격리 환경에서 인메모리 27개 테스트, migration·seed·PostgreSQL 1개 테스트 통과.
  두 workflow YAML 파싱과 필수 단계·환경 변수 존재를 검사했다.
- GitHub Actions 원격 실행 성공을 확인한 것은 아니다. 기존 웹 브라우저 테스트는
  비로그인 조회와 예전 샘플 화면을 전제로 하고 있어 인증 후 업무 검수 시나리오로 갱신해야 한다.
  전체 웹 lint 및 원격 CI 통과도 아직 별도 검증 대상이다.

## 브라우저 검수 단계 분리

- 전체 웹 ESLint 재검사: 514개 파일, 오류 0·경고 0.
- 기본 CI는 세션 없이 실행 가능한 10개 업무 경로의 로그인 이동을 검사한다.
  Cloudflare에서 10개 모두 통과했다.
- 기존 업무 브라우저 테스트의 공개 API 가정, 예전 자산 카드 이름 및 기존 결제 원장
  경로를 현재 인증·월별 원장 기준으로 수정했다. API 비교는 Bearer token을 사용한다.
- 인증 후 검수 명령은 `npm run test:e2e:authenticated`다.
  `PLAYWRIGHT_AUTH_STORAGE_STATE`(테스트 계정의 실제 세션 파일)와
  `PLAYWRIGHT_API_TOKEN`(같은 테스트 계정의 유효한 API Access Token),
  `PLAYWRIGHT_BASE_URL`, `API_URL`을 대상 테스트 환경에 맞게 지정한다.
  세션과 토큰은 비밀이며 Git에 커밋하지 않는다. 인증 테스트의 trace는 끈다.
- 세션이 없으면 실패하며 skip하지 않는다. 세션 부재 시 실패를 실제 실행으로 확인했다.
  인증 후 검수 통과는 아직 입증되지 않았다. 일반 CI 통과로 대체하지 않는다.
- 업무 API 비교 테스트는 해당 월의 테스트 업무 기록이 있는 환경이 필요하다.
  실제 운영 기록을 생성하기 위해 자동 seed를 실행하지 않는다.
- 변경한 브라우저 테스트 ESLint 및 TypeScript 검사 통과. GitHub 원격 CI 결과는 미확인.

## Linux CI 의존성 설치 복구

- GitHub Actions 조회로 API CI와 웹 CI가 모두 API 의존성 설치에서 실패함을 확인했다.
  실패 run: `33938075746`(API), `33938288916`(Web). 상세 로그 다운로드는 403이었다.
- 로컬 Linux `node:22` 컨테이너의 npm 10.9.8에서 재현:
  `npm ci`가 `vite-tsconfig-paths`의 하위 peer 의존성 `typescript@5.9.3` 잠금 항목 누락으로 실패했다.
  Windows npm 11.17.0의 설치 계획 검사에서는 드러나지 않았다.
- npm 10으로 잠금 파일을 재생성해 하위 TypeScript 항목을 추가했다.
  npm 버전 차이에 따른 libc 메타데이터 정규화도 포함한다. 앱의 TypeScript 6 버전은 유지했다.
- 수정 후 Linux npm 10 및 Windows npm 11 설치 계획 검사 통과.
  격리 Linux 환경의 실제 `npm ci`, API 단위 테스트 214개 및 Nest 빌드 통과.
  컨테이너의 읽기 전용 마운트·실행 금지 임시 영역으로 발생한 검증 환경 오류는
  운영 설정 변경 없이 임시 작업 복사본과 실행 가능한 테스트 영역으로 해결했다.
- 원격 CI 재실행의 최종 결과는 후속 확인 대상이다.

## Linux 병렬 HTTP 테스트 서버 수명

- 원격 run `33938558098`: PostgreSQL 작업 성공, 품질 작업의 인메모리 통합 테스트 실패.
- Linux·Node 22에서 동일한 lifecycle 테스트의 `ECONNRESET`을 재현했다.
  명시적으로 listen하지 않은 서버를 여러 Supertest 요청이 동시에 사용하면서
  자동 서버 종료와 다른 요청의 연결이 겹칠 수 있었다.
- lifecycle 및 PostgreSQL 병렬 테스트는 시작 시 loopback 임시 포트로 listen하고
  테스트 종료 시 app.close한다. 병렬 요청을 순차 요청으로 약화하지 않는다.
- 수정 후 Linux 전체 인메모리 통합 27개 및 Windows lifecycle 2개 테스트 통과.
- 웹 CI는 API를 함께 설치·기동하므로 `api/**` 변경도 실행 조건에 추가했다.
  API 잠금 파일 수정만으로도 웹 통합 검사 재실행이 필요하기 때문이다.

## 비로그인 CI의 Auth0 구성

- 웹 run `33938701745`의 브라우저 단계 실패를 확인했다. 원격 상세 로그는
  권한 제한으로 읽지 못했으므로 모든 실패 원인을 확정하지 않는다.
- 별도로 동일한 설정 부재를 로컬 SDK 호출로 재현했다. 환경 변수 없는
  Auth0 미들웨어는 세션 부재를 처리하기 전에 `Domain resolver threw an error`로 실패했다.
- 브라우저 CI 단계에만 실제 테넌트가 아닌 `auth.example.invalid`와 테스트 전용
  클라이언트·쿠키 설정을 제공했다. 로그인 요청은 실행하지 않으며 세션을 만들지 않는다.
  실제 로그인 검수에는 이 구성을 사용하지 않는다. 운영 환경 파일은 변경하지 않았다.
- workflow YAML에서 직접 읽은 설정으로 10개 경로의 미들웨어 처리와 세션 부재를 확인했다.
  이 검증은 전체 Next.js 브라우저 검사를 대신하지 않으며 후속 CI 결과를 확인해야 한다.
