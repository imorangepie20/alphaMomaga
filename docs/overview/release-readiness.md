# 운영 준비 검수

## 판단 기준

화면이 존재하거나 테스트가 통과했다는 이유만으로 프로젝트 전체 완료를 선언하지 않는다.
자산 → 임차인 → 계약 → 월별 청구 → 실제 수납 → 정정 및 미수 복구와
유지보수·점검·관리자 권한 흐름을 실제 데이터 저장 및 인증 경계까지 확인한다.

## 2026-09-05 확인 결과

- API 단위 테스트: 26개 파일, 207개 테스트 통과. `npm.cmd test`.
- API 빌드: `npm.cmd run build` 통과.
- 정정: API 공식 린트는 ESLint가 아니라 Oxlint다. `npm.cmd run lint` 실행 성공,
  기존 미사용 import 경고 4개가 남아 있다. 앞선 ESLint 실행 실패는 잘못 선택한 명령이었다.
- 격리된 API 통합 테스트: 21개 통과, PostgreSQL 전용 1개 건너뜀.
  PowerShell 자식 프로세스에서 `$env:DATABASE_URL=''; npm.cmd run test:e2e` 실행.
  실제 사용자 DB에 테스트 데이터를 생성하지 않았다.
- 수납 통합 검증을 강화했다. 월별 재생성의 중복 방지, 초안 수납 거부,
  승인 후 부분 수납에 따른 수납액 증가·미수 감소·청구액 불변,
  영수증 void 후 요약 원상 복구 및 취소 사유·금액 보존을 확인한다.
- Cloudflare Chromium 테스트: 비로그인 `/properties` 방문 시 `/login` 이동과
  Auth0 로그인 링크 표시 확인. 로그인 후 등록·변경 성공을 증명하는 검사는 아니다.
- 로컬 `/health/database` 조회 결과는 `ok`. 저장·동시성·복구 검증을 대신하지 않는다.

## 이번에 수정한 근본 원인

`DatabaseService.health()`는 지연 생성되는 pool에 optional query를 호출해,
첫 DB 접근 전에는 쿼리를 실행하지 않고 `ok`를 반환했다.
연결 pool 생성을 ORM과 상태 확인이 공유하도록 수정했다.
첫 상태 확인의 실제 쿼리, 연결 실패 시 오류 응답, pool 재사용 및 종료를 테스트한다.
회귀 테스트 2개가 기존 코드에서 실패하고 수정 후 통과하는 것을 확인했다.

## 남은 검수와 개발

후속 검증으로 격리 PostgreSQL 및 소규모 백업·복원 리허설은 통과했다.
각 항목의 전체 운영 요건이 모두 완료된 것은 아니며 아래 추가 결과와
`docs/overview/database-recovery.md`에서 검증 범위를 구분한다.

1. 운영 DB와 분리된 PostgreSQL 환경에서 migration, 수납 저장·중복·void·동시성 검증.
2. 실제 로그인 세션에서 역할별 접근과 등록·수정·실패 복구 및 모바일 폼 검수.
3. 테스트 전용 Auth0 계정으로 초대 링크 사용·역할 변경·차단을 검증하고
   기존 토큰의 권한 유효기간과 관리자 감사 기록 정책을 확정.
4. 백업 및 복원 리허설, 운영 배포·재시작·장애 관찰 절차 검증.
5. 기존 문서에 남긴 고급 기능을 구현 또는 명시적인 범위 결정으로 정리.
   호실 원장 기반 점유율, 비용 원장, 시스템 설정 영속 수정 등의 미구현 사항을
   화면에서 제공되는 것으로 오인하게 만들지 않는다.

위 항목은 이번 테스트만으로 완료되지 않았다. 후속 작업자는 검증 근거를 추가하며 진행한다.

## 격리 PostgreSQL 검증 추가

- 운영 DB와 다른 임시 `postgres:16-alpine` 컨테이너의 빈 DB에 migration 3개를 적용했다.
- PostgreSQL 통합 테스트를 보강하고 통과했다. 동시 청구 생성의 유일성,
  부분 수납·void 복구, 잔액을 초과하는 두 동시 수납 중 한 요청만 성공,
  API 인스턴스 재생성 후 잔액·취소 영수증 보존, 동시 void의 단일 잔액 복구를 검증했다.
- 테스트는 이제 `DATABASE_URL`만 설정해서 실행되지 않는다.
  별도 폐기 가능한 DB의 `TEST_DATABASE_URL`을 명시해야 한다.
  테스트 중에만 해당 값을 애플리케이션 DB 설정으로 적용하고 원래 환경을 복구한다.
  월별 생성 API는 DB 전체 활성 계약을 대상으로 하므로 운영 DB를 지정하면 안 된다.
- 재현: 임시 DB에 `DATABASE_URL`로 `npm.cmd run db:migrate`를 실행한 뒤,
  동일 DB를 `TEST_DATABASE_URL`로 지정하고
  `npm.cmd run test:e2e -- billing-postgres.e2e-spec.ts --no-file-parallelism` 실행.
- 이 결과는 단일 청구의 경쟁 조건과 API 인스턴스 재생성 검증이다.
  대규모 부하, DB 장애 복구, 실제 백업 복원 검증을 대신하지 않는다.

## 백업·복원 검증 추가

- 임시 원본 DB를 custom-format으로 백업하고 별도 빈 DB로 복원했다.
- 10개 업무 테이블의 행 수·내용 지문 및 migration 이력 3개를 확인했다.
- 복원 DB에서 PostgreSQL 수납 통합 테스트를 다시 통과했다.
- 절차와 수량은 `docs/overview/database-recovery.md` 참고.
  예약 백업·외부 보관·운영 규모 복구 시간·Auth0 복구는 별도 후속 요건이다.

## 청구 합계 기준 정정

- 발견: API 월별 요약과 임차인 원장 합계는 초안·취소 금액까지 더했으나,
  자산·수익 화면은 확정 청구만 합산해 동일 월에도 금액이 달라질 수 있었다.
- 변경: `billing-summary`와 임차인 원장 금액은 `Draft`, `Cancelled`를 제외한다.
  승인 대기·취소 건수 및 원장 개별 청구 기록은 보존한다. DB 원본 금액은 수정하지 않는다.
- 기본 대시보드와 수납 화면에 확정 청구 합계 기준을 명시했다.
  두 화면의 조회 오류 처리도 JSX 렌더링과 분리해 React 린트 오류를 해결했다.
- 기존 테스트가 초안 포함 금액을 기대해 오류를 놓쳤다. 확정 금액 기대값으로 바로잡고,
  취소·초안만 있을 때 금액 0 및 취소 기록 보존 테스트를 추가했다.
  수정 전 실패를 확인한 뒤 API 단위 테스트 208개와 인메모리 통합 21개를 통과했다.
- 웹 144개 테스트, 변경한 두 화면 ESLint 및 API·웹 빌드 통과.

## 수납 임차인 조회 장애 처리

- 발견: 수납 화면의 `getTenants()`가 설정 누락·HTTP 오류·네트워크 장애에
  고정 예시 임차인 4명을 반환해 실제 원장과 다른 이름을 연결할 위험이 있었다.
- 변경: 예시 대체를 제거하고 조회 실패를 호출자에게 전달한다.
  정상 빈 목록은 그대로 유지하며 배열이 아닌 응답은 거부한다.
  수납 페이지는 기존 오류 안내를 표시하고 등록 UI를 렌더링하지 않는다.
- 검증: 설정 누락, 401·403·500·503, 네트워크 오류, 잘못된 응답,
  정상 빈 목록 및 실제 목록에 대한 테스트와 페이지 오류 렌더링 테스트 추가.
  웹 전체 154개 테스트 및 변경 파일 ESLint 통과.

## 공개 조회 API 차단

- 자산·임차인·계약·기존 결제·정비·점검 목록 API의 비로그인 접근 누락을 발견하고 수정했다.
  외부 Cloudflare 경로의 HEAD 상태가 6개 모두 200에서 401로 바뀐 것을 확인했다.
- 웹 업무 조회도 서버 세션 토큰을 전달하도록 함께 변경했다.
  허용 API origin 검사, 리디렉션 거부, 캐시 비활성화를 적용했다.
- API 단위 208개·인메모리 통합 27개·웹 157개 테스트 통과.
  자세한 경계는 `docs/architecture/web-auth-boundary.md` 참고.
