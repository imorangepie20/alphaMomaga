# 자산 운영 현황 고도화

## 배경

기존 `/properties` 화면은 자산명, 위치, 유형, 점유율, 상태만 표시했다. 이 정보만으로는
관리자가 어느 자산의 수납, 계약, 유지보수, 점검을 먼저 처리해야 하는지 판단할 수 없었다.

## 원인

자산 목록이 `properties` 데이터만 조회하고 있었다. `property -> tenant -> contract ->
monthly_charge -> payment_receipt` 업무 흐름과 `maintenance`, `inspection`의 진행 상태가
자산 화면에 연결되지 않아 운영 위험이 화면에서 사라졌다.

## 변경 내용

- `/properties`는 해당 청구월의 자산, 임차인, 계약, 월별 청구, 유지보수, 점검을 병렬로 조회한다.
- `web/src/lib/property-operations.ts`는 자산별 활성 계약 수, 등록 임차인 수, 청구·수납·미수,
  90일 이내 계약 만료 수, 미완료 유지보수·점검 수를 계산한다.
- 상단 지표는 전체 자산, 평균 점유율, 이달 미수금, 조치 필요 자산 수를 표시한다.
- 목록 행은 기존 기본 정보와 함께 수납 및 운영 현황을 표시하며, 미수금·계약 만료·미완료 업무·검토
  상태가 있는 자산은 `확인 필요`로 표시한다.

## 데이터 해석 원칙

`properties` 모델에는 자산별 호실 총수 또는 가용 호실 정보가 없다. 따라서 임차인 수와 활성 계약 수는
표시하지만 공실 호실 수 또는 공실률을 추정하지 않는다. 이러한 값은 호실 재고 모델이 도입된 뒤에만
실제 값으로 제공한다.

## 검증

- `web/src/lib/property-operations.test.ts`에서 자산별 수납, 계약 만료, 미완료 업무 집계와
  공실 수를 임의 생성하지 않는 규칙을 검증한다.
- `npm.cmd run test -- property-operations.test.ts`
- `npm.cmd run build`

## 2026-09-05 집계 및 조회 신뢰성 보완

- 원인: 자산별 금액 집계가 `Draft`, `Cancelled`까지 포함하고 활성 계약의 기간을 검사하지 않았다.
  기존 조회 함수는 API 오류를 예시 데이터로 대체하여 실제 운영 데이터와 혼합될 수 있었다.
- 변경: 해당 월의 확정 청구만 청구·수납·미수에 포함한다. 초안은 승인 대기 건수로 별도 표시하고
  조치 필요 판단에 반영한다. 활성 계약은 기준일이 시작일과 종료일 사이인 경우만 집계한다.
- 조회: 자산 운영 화면은 `getPropertyRecords`로 실제 레코드만 조회한다. HTTP 오류, 통신 실패,
  목록이 아닌 응답은 오류로 처리하며 예시 데이터를 반환하지 않는다.
- 기준일: 서버 요청 시작 시 서울 날짜를 한 번 결정해 청구월 조회와 계약 집계에 동일하게 사용한다.
- 검증: 웹 전체 테스트 60개 통과. 초안·취소·다른 월 제외, 계약 기간과 90일 경계,
  일부 API 장애 및 네트워크 실패를 회귀 테스트로 확인했다.
- 범위: 다른 화면의 기존 예시 데이터 대체 동작은 아직 남아 있으므로 운영 신뢰성 후속 점검이 필요하다.
- 추가 검증: `tsc --noEmit`과 변경 파일 ESLint 통과. 자산 페이지의 JSX를 조회 `try/catch` 밖으로
  이동해 React 오류 경계 규칙을 준수했다. 기존 CSS 테스트의 불필요한 정규식 `s` 플래그를 제거해
  TypeScript 대상 버전과 맞췄으며, CSS 테스트 10개를 재실행해 통과했다.
- 이번 작업에서는 인증된 Cloudflare 브라우저 화면 검증은 수행하지 않았다.
