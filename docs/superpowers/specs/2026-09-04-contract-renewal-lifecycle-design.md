# 계약 갱신 및 lifecycle 설계

## 목적

관리자는 계약 종료일 이전에도 다음 기간의 계약을 등록할 수 있어야 한다. 이때 기존
계약의 수납 이력과 감사 로그는 보존하고, 같은 임차인·속성·호실에 기간이 겹치는 계약은
만들 수 없어야 한다.

## 결정

갱신은 기존 계약을 수정하거나 삭제하지 않고, 기존 계약을 기준으로 후속 계약을 생성하는
별도 명령으로 처리한다.

- 종료일 전 갱신: 기존 계약은 `Active`를 유지하고 새 계약은 `Upcoming`으로 생성한다.
- 종료일 이후 조회·변경: 종료일이 지난 `Active` 계약은 서버에서 `Expired` 상태로
  정합화한다. 새 계약의 시작일이 도래하면 `Upcoming`은 `Active`로 정합화한다.
- 이 방식은 기존 계약의 `id`를 참조하는 `Payment`와 감사 로그를 변경하지 않으며,
  다음 계약도 독립적인 `id`를 갖는다.

## API

`POST /contracts/:id/renew`

- 권한: `contract:manage`
- 입력: `startDate`, `endDate`, `monthlyRent`
- 속성, 임차인, 호실은 원본 계약에서만 가져온다. 클라이언트 입력으로 바꾸지 않는다.
- 원본 계약이 존재해야 하며 `Terminated` 상태는 갱신할 수 없다.
- 새 시작일은 원본 종료일 다음 날이어야 한다. 기간 공백과 중복을 모두 방지한다.
- 새 종료일은 새 시작일보다 뒤여야 한다.
- 새 계약은 시작일이 미래이면 `Upcoming`, 오늘이면 `Active`로 생성한다. 과거 시작일은
  허용하지 않는다.
- DB 경로에서는 원본 상태 정합화, 후속 계약 생성, `contract.renewed` 감사 로그 기록을
  하나의 트랜잭션에서 수행한다. 메모리 경로도 같은 규칙을 적용한다.

## 상태 정합화

`ContractsService`는 목록 조회와 단건 변경 전에 계약 상태를 날짜 기준으로 정합화한다.

- `Upcoming`이고 `startDate <= today`이면 `Active`
- `Active`이고 `endDate < today`이면 `Expired`
- `Terminated`와 `Expired`는 자동 전환하지 않는다.

DB에서는 정합화한 상태를 저장해 다음 요청과 감사 기록에서 같은 결과를 보장한다. 목록
조회는 필요한 레코드를 하나의 트랜잭션에서 정합화한 후 반환한다. 날짜 비교는 UTC
달력 날짜를 사용한다.

## 화면

`/contracts` 목록의 `Active` 또는 `Expired` 계약에 `갱신` 동작을 제공한다.

- 다이얼로그는 원본 임차인, 속성, 호실, 기존 종료일을 읽기 전용으로 보여 준다.
- 새 시작일은 원본 종료일 다음 날로 자동 채우고 수정하지 못하게 한다.
- 관리자는 새 종료일과 월 임대료만 입력한다.
- 성공하면 목록을 새로 고치고 후속 계약의 `Upcoming` 또는 `Active` 상태를 표시한다.
- `400`, `401`, `403`은 각각 날짜·계약 조건, 로그인, 권한 오류로 안내한다.

## 검증

- 서비스 테스트: 미래 갱신 생성, 종료일 다음 날 규칙, 중복·공백·해지 계약 거부,
  상태 정합화, 감사 이벤트
- 컨트롤러 테스트: 권한과 입력 오류
- 웹 테스트: 보호된 갱신 BFF URL과 본문
- TypeScript 검사, API 전체 테스트, 웹 관련 단위 테스트, 인증 redirect Playwright 테스트

## 범위 제외

- 계약서 파일 업로드와 전자서명
- 보증금, 관리비, 인상률, 자동 수납 생성
- 계약 삭제: 수납과 감사 이력 보존을 위해 별도 취소 정책이 확정되기 전까지 제공하지 않는다.
